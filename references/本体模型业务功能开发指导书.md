## 0. 文档目的与读者

本文档回答一个问题：**拿到一个全新的业务本体模型，如何在技术底座之上，完整、规范、可运行地落地成一套业务功能。**

读者为：负责基于本体模型做增量开发的 AI 助手与开发人员。

核心约定（贯穿全文）：

1. **底座不动**：技术底座是只读基线，新功能一律在业务工程中开发（先整体复制一份）；
2. **模型是唯一语义来源**：所有表、接口、页面、菜单、权限、流程、规则都必须能回溯到某个本体模型元素，禁止"模型一套、代码一套"；
3. **遵循两大规范**：开发过程完全遵守《AI 原生应用技术架构设计文档》与《UI-UE 界面设计规范》；
4. **AI 原生**：新功能必须实现右侧 AI 对话框的自然语义对话能力（本文第 7 章）；
5. **漂移靠机制不靠自觉**：模型与代码的一致性必须有可执行的对账工具与提交门禁（本文 §0.8）。

## 0.5 核心思想（必读）

> 这一节是整本指导书的总纲。后续所有章节的条款，都是这一节的具体落地。**开发任何功能前先读完本节。**

### 0.5.1 一句话

**把"业务是什么"从代码里抽出来，写成一份可执行的模型文件；代码只是这份模型文件的投影，而不是它的二次翻译。**

传统做法：先写需求文档 → 再写代码 → 文档过期，代码成为唯一真相。

本体驱动做法：模型是唯一真相，代码是它的编译产物。

### 0.5.2 需求文档与本体模型的区别（项目成败的关键）

| 维度 | 需求文档 | 本体模型 |
|---|---|---|
| 形态 | 散文 + 图表，供人阅读 | 结构化声明，供机器执行 |
| 约束力 | 描述"应该怎样" | 违反即抛异常 / 拒绝执行 |
| 变更成本 | 改文档 + 改代码 + 人工对齐 | 改模型 → 代码自动跟随 |
| 验证方式 | 评审、抽查 | 可机械比对、可回归 |

**一个项目是不是真做了本体建模，只看一件事：改模型，能不能不改代码就改变系统行为；代码和模型不一致时，谁先发现。**

### 0.5.3 唯一语义源与两条投影链路

模型不是设计稿，是**运行时的输入**。这条链路有两个断面：

```
                    ┌─────────────────────────────────────┐
                    │  本体模型 YAML（唯一语义源）          │
                    │  11 个模型文件 + manifest.json      │
                    └──────────────┬──────────────────────┘
                                   │
              ┌────────────────────┴────────────────────┐
              │ 编译期投影（构建期，一次）                │ 运行期投影（启动 + 调用，每次）
              ▼                                          ▼
    ┌──────────────────┐                  ┌──────────────────────────────┐
    │ codegen 插件      │                  │ ModelRegistry（语义注册表）   │
    │ M1 + MM → PO/DDL │                  │ 启动期加载 YAML + sha256 校验 │
    └──────────────────┘                  └───────────────┬──────────────┘
              │                                          │
              │            ┌─────────────────────────────┼─────────────────────┐
              │            │                             │                     │
              ▼            ▼                             ▼                     ▼
        PO 类          目标态 DDL              行为分发（权限→规则→Handler→事件）  AI 工具 schema
                                                        │                     │
                                                        ▼                     ▼
                                                  流程/场景引擎          LLM 的接口说明书
```

**关键认识：模型同时驱动了"机器做什么"和"人怎么问"。** 这不是两套东西：

- 权限校验读 `M2.requiredPermissions`；
- 规则求值读 `M2.appliedRules`，按 `rule.engine` 路由表达式引擎；
- Handler 反射调用读 `@BehaviorHandler` 绑定的行为 ID；
- 事件产出读 `M2.producedEvents`；
- AI 的系统提示词注入 `ModelRegistry` 摘要，AI 工具（行为描述 / 导航 / 只读 SQL）的 schema 直接从注册表生成。

模型一变，AI 的知识面自动跟着变——**不需要再维护一份"AI 知识库"，因为它本来就是模型的投影。**

### 0.5.4 分层职责：一个事实只在一个地方定义

本体驱动的常见失败是"模型一套、代码一套"。根治办法是**分层划清职责，每个事实只有一个真源**：

| 层面 | 唯一语义源 | 保障机制 |
|---|---|---|
| 业务语义 | **M1**（有什么字段、什么含义） | PO 字段与类型完全由 M1 渲染，无法漂移 |
| 映射契约 | **MM**（落到哪张表、哪一列、什么类型） | M1↔MM 双向校验器；表名列名不再硬编码 |
| 行为契约 | **M2**（做什么、谁能做、受什么约束） | `BehaviorDispatcher` 按 M2 驱动，不在代码里写死流程 |
| 规则契约 | **M3**（凭什么拒绝） | 规则引擎统一求值，通过/失败均落日志表 |
| 事件契约 | **ME**（跨对象怎么联动） | outbox 同事务写入 → 派发 → 幂等 → 重试 → 死信 |
| 权限契约 | **M5**（谁能看到什么） | 权限码双端控制：M5 声明 ↔ 种子入库 ↔ 代码引用三方对账 |
| 界面契约 | **MU**（从哪进、有哪些操作点） | 菜单与路由对账器，漂移即阻断提交 |

**工程约定（如子包名、是否继承基类、主键策略）不表达在模型里，集中在 `PoMapping` 一处**——这是刻意为之：把 M1/MM 都表达不了的东西收到一个文件，而不是散落。

### 0.5.5 漂移必须被机制发现，而不是靠人盯

模型驱动最容易失败的地方不是建模，而是**建模之后模型与代码慢慢分家**。因此对账工具与提交门禁是方法论的硬组成部分，不是可选项：

- 编译期：M1 + MM → PO / DDL 自动生成，物理层不允许手写；
- 启动期：`ModelRegistry.validateReferences()` 校验全部跨模型引用，不一致直接阻断启动；
- 提交期：`PoFieldDiffReporter` / `MenuRouteChecker` / `BehaviorRegistryChecker` 三项对账，发现漂移即**拒绝提交**；
- 运行期：事件产出方 / 消费方闭环统计，识别"事件产出后无人消费"这类静默失败。

**一个项目第一次跑守门员就抓到大量漂移，是正常且必要的**——它证明模型驱动此前并未闭环。详见 §0.8。

## 0.6 模型体系：七模型与十一模型（重要澄清）

> **常见疑问：现在到底该用几个模型？** 本节给出明确答案。

### 0.6.1 两个版本的由来

| 版本 | 模型集合 | 特征 | 适用 |
|---|---|---|---|
| **v9.0 七模型** | M1 / M2 / M3 / M5 / M6 / M7 / MU | 单体同步部署，跨对象联动靠 `syncTriggers` 同步调用 | 中小型单体业务系统 |
| **十一模型** | M1 / M2 / M3 / M4 / M5 / M6 / M7 / ME / MI / MM / MU | 在七模型基础上加回 **M4 场景模型**、**ME 事件模型**、**MI 接口模型**、**MM 对象-数据表映射模型** | 事件驱动、含外部系统集成、需构建期代码生成 |

v9.0 的裁剪说明（原文摘自《本体驱动软件建模方案 v9.0》）："移除四个模型：ME 事件模型、M4 场景模型、MM 对象-数据表映射模型、MI 接口模型"，改以"同步流程编排"替代"事件驱动解耦"。

### 0.6.2 如何选择

**判断标准：是否需要事件驱动的跨系统联动、是否有外部系统集成、是否需要在构建期生成持久层代码。**

- 三者皆否 → **七模型**即可，更轻量，无事件基础设施负担；
- 任一为是 → **十一模型**。多出的四个模型各自解决一个七模型覆盖不到的问题：
  - **ME 事件模型**：跨聚合/跨系统联动（禁止跨聚合同步调用，见 §0.6.4）；
  - **MM 映射模型**：表名列名的唯一真源，是构建期代码生成的前提；
  - **MI 接口模型**：与外部系统（WMS / TMS / SAP）的契约与边界；
  - **M4 场景模型**：跨行为的长事务编排（BEHAVIOR_CALL / EVENT_WAIT / RULE_CHECK / SUB_SCENARIO 四类步骤）。

### 0.6.3 十一模型在七模型基础上的增量

| 模型 | 职责 | 在七模型中如何临时替代 |
|---|---|---|
| **M4** 场景 | 长事务编排、跨行为等待 | 无替代，必须用 M6 流程串，但无法表达"等待某事件" |
| **ME** 事件 | 领域事件定义与订阅关系 | 用 M2 `syncTriggers`（同步调用，只能同事务） |
| **MI** 接口 | 外部系统契约 | 无标准位置，易退化为散落在集成层的临时代码 |
| **MM** 映射 | 物理表列契约 | 手工维护 DDL，模型与表极易漂移 |

### 0.6.4 两种路线的关键差异：跨对象联动

| 维度 | 七模型（同步） | 十一模型（事件驱动） |
|---|---|---|
| 联动载体 | M2 `syncTriggers`：行为成功后**同步调用**下游行为 | ME 事件：行为产出事件 → outbox → 派发 → 订阅者消费 |
| 事务边界 | 同一事务内顺序完成 | 事件与业务写同事务；消费端独立事务 |
| 可靠性 | 靠事务回滚 | 幂等日志 + 重试 + 指数退避 + 死信 + 启动恢复 |
| 适用 | 进程内单体 | 跨系统、需要最终一致 |
| 硬约束 | 一个行为只改一个聚合 | **跨聚合禁止直接调用，一律经事件** |

> 十一模型路线下，"事件产出后无人消费"是最高频的静默缺陷。**必须有闭环对账工具**统计 `producedEvents` 与 `subscribedEvents` 的交集覆盖率，否则模型声明会大量空转。

### 0.6.5 本技能包内的两套底座

| 底座 | 路径 | 模型体系 | 技术栈 | 状态 |
|---|---|---|---|---|
| `techbase/`（Python 参考实现） | `<技能根目录>/techbase/` | 七模型 | Python 3.10 + Flask + SQLite + React/TS | 可运行 |
| `jjy-ontology-base/`（Java 通用底座） | `<技能根目录>/jjy-ontology-base/` | 十一模型 | Java 8 + Spring Boot 2.7 + MyBatis-Plus + MySQL 8 | 可独立构建，已验证 |

**`jjy-ontology-base/` 规格**（包名 `com.jjy`，artifactId `jjy-ontology-base`）：

| 项 | 内容 |

| 模块 | `codegen-maven-plugin` + `jjy-domain` + `jjy-infrastructure` + `jjy-application` + `jjy-interfaces` + `jjy-boot`（6 个 Maven 模块） |

> ⚠ **重要**：`jjy-ontology-base/` 使用十一模型（含 ME/M4/MM/MI），与《本体驱动软件建模方案 v9.0》的七模型裁剪方向**不一致**。这不是错误——十一模型是 v9.0 之前（以及事件驱动场景下）的完整形态，Java 底座走的是这条路。**开发时选定一条路线并保持全程一致**，切勿在同一工程内混用两套模型体系（详见 §0.6.6）。

### 0.6.6 路线一致性检查（开工前必做）

| 检查项 | 七模型路线 | 十一模型路线 |
|---|---|---|
| `models/` 下 YAML 文件数 | 7 | 11 |
| `manifest.json` 的 `model_files` | 登记 7 个 | 登记 11 个 |
| `manifest.json` 的 `modelCount` | 7 | 11 |
| 是否有 `mm-mapping-model.yaml` | 无 | 有，且**必须**含全量表映射 |
| `ModelLoader` 加载的模型数 | 7 | 11 |
| 是否有事件基础设施（outbox / 幂等 / 死信） | 无 | 有 |
| M2 `syncTriggers` | 常用 | 一般不用，改用 `producedEvents` / `subscribedEvents` |

> 混用的典型症状：模型声明了 `producedEvents`，但运行时没有 outbox 写入 → 事件永远不产生；或模型里引用了 `mm-mapping-model.yaml`，但构建期没接 codegen → PO 与模型漂移。**开工第一件事是确认本工程的模型体系，并让 `manifest.json` 与 `ModelLoader` 与之一致。**

## 0.7 达成判据：L1 / L2 / L3 / L4（验收的唯一标准）

> 回答"这功能到底做完没有"。**不要用"代码写完了"或"测试通过了"代替本节判据。**

### 0.7.1 四层定义

| 层级 | 名称 | 判定条件 | 核实方式 |
|---|---|---|---|
| **L1** | 已声明 | 模型 YAML 中存在该声明，且跨模型引用完整 | 读 YAML + 启动期 `validateReferences()` |
| **L2** | 已实现 | 代码里有对应实体且有**实质逻辑**（PO / Handler / 页面存在，Handler 有真实 DB 写与状态变更，不是空壳） | 静态比对：实体存在 + Handler 含 DB 写或状态变更 |
| **L3** | 已接通 | 链路两端真的连上：调用方能触发、产出物能被下游消费、异常可观测、失败有重试与死信 | 运行验证：触发 → 产出 → 消费 → 落库 |
| **L4** | 可验收 | L3 成立，且有自动化测试或可复现证据覆盖该链路（含正常、边界、逆向、异常路径） | 测试断言：真实行为 ID 被测试引用 |

### 0.7.2 为什么必须拆四层（本方法论最贵的一课）

**L2 有极强的伪装性。** 行为全部有实现、代码读起来"该有的都有"，但缺陷藏在**接线的接缝处**。实测典型分布：L2 达成率 98%+，L3 在事件维度仅 15%。

只做 L2 统计必然得出乐观且错误的结论。

### 0.7.3 判据矩阵的使用规则

| 规则 | 说明 |
|---|---|
| 逐条判，不抽样 | 每条需求落到 L1–L4 之一，不允许"大致覆盖""大部分实现"这类表述 |
| L2 需证据 | Handler 须有 DB 写或状态变更；仅 `return ok()` 不算实现 |
| L3 需双向 | 既有产出方、也有消费方，且中间无静默失败点 |
| L4 需资产 | 指向具体测试类与断言数，不接受"手工验证过" |
| 缺口即待办 | 每条卡在 L1–L3 的需求自动进入待办清单，并标注卡点 |

### 0.7.4 三种验收方式不可互相替代

| 方式 | 怎么做 | 适用层级 |
|---|---|---|
| 机械比对 | 脚本比对模型声明与代码实体，输出覆盖率 | L1 / L2 |
| 运行验证 | 启动系统跑真实链路，看事件是否产生、是否被消费、是否落库 | L3 |
| 测试断言 | 以真实行为 ID 编写的集成测试，断言事件链与状态变更 | L4 |

> **本方法论最关键的一条经验**：用 L1/L2 的方法（读代码、比对声明）去回答 L3/L4 的问题（链路通了吗、能验收了吗），必然得出偏乐观的结论。**机械比对只能证明"零件在"，不能证明"机器能开"。**

### 0.7.5 验收执行顺序

```bash
# ① 编译闸门（最快，先排除语法/依赖断裂）
mvn -o compile -DskipTests

# ② 模型-代码对账（L2 覆盖率）
python scripts/check-model-drift.ps1
python scripts/check-model-db-alignment.py

# ③ 事件闭环对账（L3 覆盖率）
#    统计 producedEvents 与 subscribedEvents 的交集

# ④ 单元与集成测试（L4 证据）
mvn -o -pl <application模块> -am test

# ⑤ 业务链路端到端走查（业务验收）
#    以真实行为 ID 驱动，断言事件链与状态流转
```

### 0.7.6 验收判定规则

- 每条需求必须有明确层级结论，**L3/L4 的缺口不允许用"L2 已达成"抵扣**；
- 验收结论必须写明卡在哪一层、缺什么、谁负责；
- 没有测试资产的业务链路，最高只能判到 L3；
- 外部系统集成只有 mock 实现的，最高只能判到 L2。

## 0.8 漂移守门员（Model-vs-Code Drift Guard）

> **这一节是 v2.0 相对 v1.0 最重要的增量。** v1.0 把"模型与代码一致"写成纪律；v2.0 把它做成机制。

### 0.8.1 目的

把"改 M1 模型必须同步改 PO / 改 MU 模型必须同步改路由"这条铁律**刻进 Git**，让模型驱动不再依赖人记得。

### 0.8.2 十一项检查

前 3 项对账「模型 ↔ 代码结构」，后 8 项管更隐蔽的漂移（模型自相矛盾、声明了却无人消费、状态机闭合、行为形态三方一致等）。

| # | 检查项 | 模型端 | 代码端 | 工具 |
|---|---|---|---|---|
| 1 | M1 对象模型 ↔ Java PO | `models/m1-object-model.yaml` | `infrastructure/.../po/*PO.java` | `PoFieldDiffReporter` |

### 0.8.5 manifest 哈希登记

`manifest.json` 的 `model_files` 支持两种 schema：

```json
// 新契约（推荐）：对象数组 + sha256，启动期校验
{ "file": "m1-object-model.yaml", "sha256": "c8d2b1b4..." }
```

- 旧契约：字符串数组（纯文件名），视为"未校验"，启动期仅 WARN；
- 新契约：带 `sha256`，启动期比对；不一致**仅 WARN 不阻断**（模型被合法修改后忘了重算很常见，硬阻断会误伤开发）。

改完模型后重算：

```powershell
.\scripts\regenerate-manifest.ps1
```

## 0.9 Java 底座的模型驱动实现（Java 栈必读）

> 本节描述 `jjy-ontology-base/` 里已经落地的模型驱动机制。
> Python 栈的等价能力见 §2 映射总表；本节只讲 Java 栈**特有**的部分。

### 0.9.1 行为形态：模型声明「这个行为由谁实现」

M2 的 `behaviorForm` 字段是行为层自动化的**唯一判据**。

| 形态 | 含义 | 实现方式 |
|---|---|---|
| `TEMPLATE` | 模板生成 | codegen 生成 Handler 骨架（CRUD 类标准动作） |
| `HANDWRITTEN` | 手写实现 | 开发者自己写（**默认值**，不写该字段即为此值） |
| `SCRIPT` | 脚本实现 | 由 `actionScript` 驱动（预留；Java 8 无 Nashorn，暂不支持） |
| `DECLARATIVE` | 纯声明 | 无本地代码，由引擎按 M7/规则/事件通用执行 |

**为什么需要它**：没有这个字段，生成器只有两个选择——「全都生成」（与手写实现冲突）
或「全都不生成」（等于没有自动化）。

**模板形态**：`behaviorForm=TEMPLATE` 时用 `templateKind` 指定具体模板。

| templateKind | 生成的行为 | 说明 |
|---|---|---|
| `DELETE` | 按主键逻辑删除 | flag 置 1 |
| `UPDATE` | 按主键更新可变字段 | 可更新字段集由 M1 推导（**不含 status**，状态归状态机管） |
| `BATCH_DELETE` | 按条件批量逻辑删除 | 无条件时拒绝执行（防误删全表） |
| `QUERY_PAGE` | 分页查询 | 走 M7 报表口径 |

```yaml
- id: Product_Update
  name: 更新商品
  ownerEntity: Product
  behaviorType: COMMAND
  triggerType: USER_ACTION
  behaviorForm: TEMPLATE
  templateKind: UPDATE
  postconditions: []
  requiredPermissions:
    - PERM-PRODUCT-ADD
```

### 0.9.2 生成物落在 `src/`，用内容指纹保护

生成物落在 `src/main/java/.../handler/generated/<alias>/`，**进版本库**——
开发者可以直接改它，不必另建类。

代价是「模型改了会不会冲掉我的修改」。解法是**内容指纹**：

| 情形 | 处理 |
|---|---|
| 文件不存在 | 生成 |
| 指纹与「去掉指纹行后的内容摘要」一致 | 说明开发者没改 → 安全刷新（模型变更同步进来） |
| 指纹不符 | 说明开发者改过 → **跳过，不覆盖**，构建期告警 |

> 指纹是「内容的摘要」，不是「内容的副本」——
> 用文件里存的指纹去和新内容比较是错的（内容没变时两者本就相等，
> 会把「开发者改过」误判成「未改动」而覆盖掉）。

**配套的安全前提**：`BehaviorHandlerRegistry` 从「覆盖语义」改为「重复即报错」。
否则生成物与手写实现共存时，「谁生效」取决于 Spring 的 bean 扫描顺序——
一个不确定且无任何提示的行为。**引入生成机制前，必须先让「重复实现」从静默变响亮。**

### 0.9.3 生成物里不出现硬编码的业务语义

生成的 Handler 遵守与手写代码**相同**的铁律：

```java
String table = physicalMapping.tableName("Product");   // 表名 → MM 模型
String pk = physicalMapping.pkColumn(table);             // 主键列 → MM 模型
Object pkObj = dto.get("productId");                    // 主键字段 → M1 模型
String flagCol = physicalMapping.column(table, "flag");  // 列名 → MM 模型
```

状态目标值来自 M2 的 `postconditions`，查询口径来自 M7，
权限与规则由 dispatcher 按 M5/M3 校验。
**过程可以手写，但过程中的每一个「是什么」都问模型。**

### 0.9.4 ABAC：属性级授权必须真执行

M5 的 `permissions[].abacCondition` 声明属性级约束（如「只有本人能改自己的单」）。
声明了却不被执行，等于没声明。

**RBAC 与 ABAC 的分工**：

| | 决定 |
|---|---|
| RBAC（角色 → 权限） | 能不能做这个动作 |
| ABAC（属性 → 条件） | 能不能碰这一条数据 |

两者都要过：RBAC 放行后，ABAC 再逐条判定。

**表达式语法**与 M3 规则一致（Aviator 5.3），可用变量：

| 变量 | 含义 |
|---|---|
| `actor.*` | 当前用户属性（userId / username / userType / customerId / roles…） |
| `row.*` | 目标记录属性（来自聚合根当前状态） |
| `ctx.*` | 上下文（domain / behaviorId） |

示例：`row.ownerId == actor.userId`、`row.amount <= actor.limitAmount`。

**求值失败按拒绝处理**（fail-closed）——属性级授权宁严勿松。

### 0.9.5 界面也由模型驱动

MU 的 `screens[].elements[]` 声明界面元素（类型、必填、字典绑定、列宽），
`actions[]` 声明操作点（对应哪个 M2 行为）。

后端 `GET /meta/screens/{screenId}` 把声明归一化后交出：

```json
{
  "screenId": "FrmProductMaintain",
  "screenType": "MAINTAIN",
  "isMaintainScreen": true,
  "layout": "SINGLE_TABLE",
  "inputElements": [ { "id": "productName", "type": "TEXT", "required": true } ],
  "tableColumns":  [ { "id": "productName", "label": "商品名称", "width": null } ],
  "actions":       [ { "id": "submit", "name": "提交上架", "behaviorRef": "Product_Submit", "primary": true } ]
}
```

前端 `ModelScreen.vue` 组件按此渲染表单、表格与按钮——
**前端文件里没有一个字段名、按钮名、行为名的硬编码**。

新增界面时：MU 加一个 screen → 前端加一个 10 行的 Vue 文件 → router 加一条路由。

### 0.9.6 M7 结果行按模型字段名返回

M7 的 `resultColumns` 声明的是**模型字段名**（`productName`，camelCase），
而 JDBC 返回的是**物理列名**（`product_name`，snake_case）。

不回映射的话，返回行的键全是 snake_case，前端按模型字段名取不到值——
**M7 声明的语义在返回处断了**。`QueryReportExecutor` 据 MM 的列映射把行键回映射为模型字段名。

### 0.9.7 声明消费点：规则表自动推导

第 8 项检查（「模型声明了但代码不消费」）如果手工维护规则表，
就会产生**守门员自己的盲区**：新增一个模型语义字段时忘了加规则，
它就退化成「无人消费也不报」。

`AutoDeclarationChecker` 的做法是**扫描全部模型文件自动推导检查项**：

1. 收集每个 YAML 里出现过的所有键名；
2. 排除非语义字段（id / name / version / type…）与技术字段（flag / created_at…）；
3. 为剩余字段自动生成检查项，关键词按字段名派生（`getXxx()` 与 `"xxx"` 两种形式）。

实测推导 **100 个检查项**，自动发现 10 处真实缺口。

> **扫描范围必须包含 codegen 插件**——生成器本身就是模型的消费者
> （它把模型变成 PO / DDL / Handler）。不扫它会把「已被生成器消费」的字段
> （如 M1 的子实体声明）误报成真缺口。

## 2. 模型 → 实现 映射总表（核心）

> 这是全篇最重要的对照表。开发中遇到"这个模型元素落到代码哪里"，先查此表。

### 2.1 M1 对象模型 → 数据库表 / 表单 / 字典

| M1 元素 | 开发落地点 |
|---|---|
| `aggregates[].id/name/alias` | 表名（`alias` 转 snake_case）、业务对象别名 |
| `aggregates[].lifecycle` | 状态字段的枚举取值（`status`） |
| `attributes[].name/label/type` | 表字段 / 表单控件 / DTO 字段 |
| `type: String/Integer/Decimal/Money` | `VARCHAR/NUMBER/NUMBER` + 文本框/数字框 |
| `type: Date/DateTime` | `DATETIME` + 日期控件（`DATEPICKER`） |
| `type: Boolean` | `TINYINT` + 复选框（`CHECKBOX`） |
| `type: Enum` | `VARCHAR`（存值）+ 下拉框（`COMBO`，选项来自 `enumValues`） |
| `type: DictionaryRef` | `VARCHAR`（存 code）+ 下拉框（`COMBO`，选项来自数据字典） |
| `type: AggregateRootRef` | `VARCHAR/INTEGER`（存目标聚合根 ID）+ **跳选框（`POPUP_SELECT`）** |
| `required/unique` | 表约束 `NOT NULL` / `UNIQUE` + 前端必填/唯一校验 |
| `refRules` | 属性级校验（service 内或校验工具），见 §4.5 |
| `entities[]`（子实体，`cardinality=ONE_OR_MORE`） | 独立从表（DETAIL），外键 `xxx_id` 关联主表 |
| `entities[]`（单个，`ZERO_OR_ONE`） | 主表字段平铺 或 JSON 列 |
| `valueObjects[]` | 字段前缀平铺 或 JSON 列 |
| `invariants` | 聚合级校验（service 内，见 §4.5） |
| `data_dictionaries[]` | 注册表 `data_dictionaries` → `/api/meta/dictionaries`，自动进入数据字典 |
| `aggregate_associations[]` | 外键字段 + 查询 Join 依据 |

### 2.2 M2 行为模型 → 后端 service 方法 + API + 前端按钮

| M2 元素 | 开发落地点 |
|---|---|
| `behaviorType=COMMAND` | `services/*_service.py` 中的一个写方法（在事务内） |
| `behaviorType=QUERY` | `services/*_service.py` 中的一个读方法（或 M7 查询） |
| `triggerType=USER_ACTION` | 前端页面一个按钮，调用对应 API |
| `triggerType=SYSTEM` | 仅被 syncTriggers 调用，不暴露 REST |
| `preconditions` | service 方法开头的前置校验 |
| `postconditions`（状态变更） | service 方法中的 `UPDATE ... status=...` |

## 3. 关键约定与规范（强制）

### 3.1 编号自动生成规则

> 业务对象"编号"字段一律由系统自动生成，界面**不显示、不可编辑**（若需展示也只读）。

规则：**对象英文别名（alias）大写取前 3 位 + 4 位流水号**。

| 对象 alias | 前缀 | 示例 |
|---|---|---|
| Customer | `CUS` | `CUS0001` |
| Contract | `CON` | `CON0042` |
| Invoice | `INV` | `INV0107` |
| Receipt | `RCP` | `RCP0003` |
| Product | `PRD` | `PRD0012` |

参考实现（`backend/utils/codegen.py`，在**同一事务内**生成，避免并发重号）：

```python
import re
import db

def generate_code(alias: str, table: str, column: str = "xxx_no", conn=None) -> str:
    """对象英文别名前 3 位大写 + 4 位流水号，如 Customer -> CUS0001"""
    prefix = re.sub(r"[^A-Za-z]", "", alias).upper()[:3]
    row = db.query_one(
        f"SELECT MAX({column}) AS mx FROM {table} WHERE {column} LIKE ?",
        (f"{prefix}%",),
        conn,
    )
    cur = 0
    if row and row["mx"]:
        m = re.match(rf"^{prefix}(\d+)$", row["mx"])
        if m:
            cur = int(m.group(1))
    return f"{prefix}{cur + 1:04d}"
```

> 说明：`code-paas` 中示例客户编号用的是"前缀+时间戳"，仅作演示；**正式扩展开发一律采用本节的"三位前缀 + 四位流水号"规则**。

### 3.2 数据库表 5 个默认字段约定（强制）

任何新建业务表，除业务字段外，**必须追加以下 5 个默认字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `created_by` | INTEGER | 创建人（用户 ID） |
| `created_at` | DATETIME DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `updated_by` | INTEGER | 更新人（用户 ID） |
| `updated_at` | DATETIME DEFAULT CURRENT_TIMESTAMP | 更新时间 |
| `flag` | TINYINT DEFAULT 1 | 数据有效标志（1 有效 / 0 逻辑删除） |

约束：

1. 这 5 个字段**不显示在界面表单上**，由后端 service 在数据写入时**自动赋值**：
   - `created_by` / `updated_by` = 当前登录用户 `g.user_id`（经 `auth_service.current_user()` 获取）；
   - `created_at` 由 DB 默认值写入；`updated_at` 每次更新显式 `CURRENT_TIMESTAMP`；
   - `flag` 新增默认 1；删除采用**逻辑删除**（`flag=0`），不做物理删除。
2. 查询列表默认只返回 `flag=1` 的数据（`WHERE flag=1`）。
3. 该约定与架构文档 §11.2 的映射策略并行：聚合根→主表、子实体→从表，主从表都带这 5 个字段。

参考 DDL：

```sql
CREATE TABLE IF NOT EXISTS contract (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    contract_no  VARCHAR(50) UNIQUE NOT NULL,   -- 系统自动编号
    contract_name VARCHAR(100) NOT NULL,
    -- ……业务字段……
    status VARCHAR(30) DEFAULT '草稿',
    created_by INTEGER,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_by INTEGER,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    flag TINYINT DEFAULT 1
);
```

### 3.3 控件类型映射规则（强制，对齐 MU §8.3）

| M1 属性类型 | 界面控件 | 说明 |
|---|---|---|
| Date / DateTime | `DATEPICKER`（`type="date"`） | 日期控件 |
| Enum | `COMBO`（下拉框） | 选项来自 `enumValues` |
| DictionaryRef | `COMBO`（下拉框） | 选项来自数据字典（label 显示、code 存储） |
| **AggregateRootRef** | **`POPUP_SELECT`（跳选框）** | 文本框 + 右侧按钮弹窗选择 |
| Boolean | `CHECKBOX`（`type="checkbox"`） | 复选框 |
| String（长文本/备注） | `TEXTAREA` | 多行文本域 |
| Integer/Decimal/Money | `NUMBER`（`type="number"`） | 数字框 |
| 其它 String | `TEXTBOX` | 文本框 |

要点：

- **对象引用（AggregateRootRef）必须用跳选框**：点击弹出目标对象的选择列表（分页 + 关键字），选中后回填显示名与 ID；
- **枚举 / 数据字典必须用下拉框**；
- 下拉框数据来源：枚举用 `enumValues`；数据字典经注册表 `/api/meta/dictionaries` 返回。

### 3.4 数据字典自动注册

M1 中 `data_dictionaries` 里配置的字典项，由 `ontology/registry.py` 在启动时解析进 `registry["data_dictionaries"]`，前端经 `/api/meta/dictionaries` 获取即可渲染下拉框，**无需手工再建字典数据**。

> 若字典项需要在运行期维护（增删改），再扩展字典维护功能；建模期配置的静态字典项默认只读生效。

### 3.5 主从表单：单事务 + 从表外键自动赋值（强制）

主从表（`MASTER_DETAIL_FORM`）保存必须满足：

1. **同一事务**：主表 insert + 从表批量 insert/delete 在**一个 `db.transaction`** 内完成，任一失败整体回滚；
2. **从表外键自动赋值**：先插入主表拿到主键 `master_id`，再为每个从表行自动写入 `{master}_id = master_id`（从表外键不在界面上让用户填写）；
3. **从表全量重建**：更新时按主表主键先逻辑删除（`flag=0`）或物理删除旧从表行，再按当前提交的行重新插入，保证与界面行一致。

参考实现：

```python
def save_with_details(master, details, user):
    def _do(conn):
        master["xxx_no"] = generate_code("Contract", "contract", "contract_no", conn)
        mid = db.execute(
            "INSERT INTO contract (contract_no, contract_name, ..., created_by, updated_by) VALUES (?,?,?,?,?)",
            (master["contract_no"], master["contract_name"], ..., user["id"], user["id"]),
            conn,
        )[0]
        for d in details:
            db.execute(
                "INSERT INTO contract_stage (contract_id, stage_name, ..., created_by, updated_by) VALUES (?,?,?,?,?)",
                (mid, d["stage_name"], ..., user["id"], user["id"]),   # 外键自动 = mid
                conn,
            )
        return mid
    db.transaction(_do)
```

### 3.6 规则模型完整实现要求（强制）

> 用户要求：规则模型中的规则必须**完整实现**，不允许只建模不落地。

规则分三层落地，都必须真实生效：

| 层级 | 模型位置 | 落地方式 | 触发时机 |
|---|---|---|---|
| 属性级 | M1 `attributes[].refRules` | service 保存时逐字段校验 | 保存/提交前 |
| 聚合级 | M1 `invariants` | service 保存时聚合内校验 | 保存/提交前 |
| 跨对象级 | M3 `rules[]` | 规则引擎统一求值（`simpleeval`） | 行为执行中（appliedRules）或 syncTriggers 条件 |

参考实现（规则引擎，`backend/utils/rules.py`）：

```python
from simpleeval import simple_eval

def evaluate_rule(expression: str, params: dict):
    """执行 M3 规则表达式，返回布尔或结果值。params 由 inputParams 映射。"""
    return simple_eval(expression, names=params)

def check(rule, params):
    """校验规则，不满足则抛业务异常（带 violationMessage）。"""
    ok = evaluate_rule(rule["expression"], params)
    if not ok:
        raise ValueError(rule.get("violationMessage") or f"规则 {rule['name']} 校验不通过")
```

service 内调用示例（对应 M2 的 `appliedRules`）：

```python
from utils.rules import check
from ontology.registry import registry

def submit(customer_id, user):
    # ... 前置校验
    rule = registry["rules"].get("RULE-XXX-ELIGIBLE")
    if rule:
        check(rule, {"customerType": customer["customer_type"], "amount": customer["amount"]})
    # ... 状态变更
```

> `M1 refRules`/`invariants` 若用简单表达式表达，同样走 `simple_eval`；若表达式复杂（含聚合内求和等），在 service 内写等价 Python 逻辑并保证语义一致。**规则失败必须给用户明确的中文提示。**

### 3.7 权限码与资源约定

- 权限码命名：`{域}:{对象}:{动作}`，如 `customer:save`、`contract:submit`、`system:user:add`；
- 行为级权限码写在 M5 `permissions[].permissionId`，并同时出现在 M2 `requiredPermissions`；
- 菜单级资源 `permission_code` 控制菜单可见性（如 `contract:query`）；系统/流程类菜单用 `system:manage` / `flow:manage`，仅 admin 可见；
- 后端写接口用 `@require_permission('customer:submit')` 保护；admin 角色（`code=admin`）返回 `*` 通配放行。

### 3.8 API 约定与统一响应

- 前缀 `/api`；分页参数 `page`（默认 1）、`size`（默认 10）；
- 统一响应：`{ success, message, data, errorCode, traceId }`；
- 业务异常统一抛 `ValueError`，由全局错误处理器转成 `{ success:false, message }`；
- 写接口一律 `login_required` + `require_permission`。

### 3.9 前端页面约定

## 4. 开发流程详解（步骤 1～10）

### 步骤 1：编写本体模型 YAML

在 `code-app/models/` 编写/扩展模型文件。**先按 §0.6 确认本工程的模型体系（七模型或十一模型），并全程保持一致。**

建模顺序建议（参考框架 §10.1）：

`M1 对象 → M5 角色 → M3 规则 → M2 行为 → M7 查询 → M5 权限 → M6 流程 → MU 界面`

十一模型路线追加（放在 MU 之后）：

`ME 事件 → MI 接口 → MM 映射 → M4 场景`

> **顺序有讲究**：MM 必须晚于 M1（MM 描述的是 M1 字段的物理落点，M1 未定时 MM 无从写起）；ME 必须晚于 M2（事件由行为产出）。

YAML 结构与字段语义严格对齐《本体驱动软件建模方案 v9.0》，可直接参照技能内 `reference-example/` 下 7 份黄金范例 YAML 与 `code-app/models/` 中已有文件。

> 十一模型路线另可参照 `jjy-ontology-base/models/` 下的 11 份 YAML（含 ME/MI/MM/M4 的完整样例）与该底座的 `models/README.md`。

### 步骤 2：注册到 manifest 与注册表

将新增/修改的模型文件登记进 `models/manifest.json` 的 `model_files`：

```json
{
  "model_type": "MANIFEST",
  "version": "1.0",
  "domain": "销售合同执行管理",
  "project": "contract-management",
  "model_files": [
    "m1-object-model.yaml",
```

十一模型路线追加 `m4-scenario-model.yaml`、`me-event-model.yaml`、`mi-interface-model.yaml`、`mm-mapping-model.yaml`，并建议补齐 `modelCount` 与 `build_order`（见 §0.8.5 的新契约）。

`ontology/registry.py` 启动时按 `model_type` 分派注册（OBJECT/BEHAVIOR/RULE/ACTOR/FLOW/REPORT/UI）。**若新增了 M3 规则模型，需确认 registry 已把 `rules[]` 注册进 `registry["rules"]`（框架文档已定义该结构，`_register` 已覆盖 RULE 分支，如需可补齐）。**

### 步骤 3：M1 → 数据库表生成

**Python 栈**：在 `schema.sql` 追加业务表 DDL：

- 聚合根 → 主表；子实体（`ONE_OR_MORE`）→ 从表（外键 `{master_alias}_id`）；
- 每个字段按 §2.1 映射为 SQL 类型；
- `required` → `NOT NULL`；`unique` → `UNIQUE`；
- 追加 5 个默认字段（§3.2）。

**Java 栈（十一模型路线）**：**不手写 PO，也不手写业务表 DDL。** 分工是：

| 文件 | 角色 | 维护方式 |
|---|---|---|
| `models/m1-object-model.yaml` | 业务语义（聚合、字段、类型、必填） | 随模型改 |
| `models/mm-mapping-model.yaml` | 映射契约（表名、列名、列类型） | 随模型改 |
| `target/generated-sources/po/**` | Java 实体类 | **自动生成**（codegen 插件） |
| `target/generated-sources/ddl/*.sql` | 目标态 DDL | **自动生成**（codegen 插件） |
| `db/migration/V1__full_schema.sql` | 物理结构快照（Flyway 实际执行） | 导出真实库后手工维护 |

- codegen 在 `generate-sources` 阶段执行，产物不入 Git，每次编译重新生成；
- MM 是表名列名的唯一真源，**表名、列名、列类型不在 Java 代码里硬编码**；
- 迁移文件仍需手工维护，因为索引、默认值、字符集、表注释是 MM 不表达的信息；
- **漂移由校验兜底**：MM ↔ DB 对账脚本检查表、列、类型，不一致即失败退出。

### 步骤 4：数据字典自动注册

M1 字典无需额外代码，启动即生效。前端通过 `metaApi.dictionaries()` 取用。

### 步骤 5：M2 行为 + M3 规则 → service 实现

- 方法内：前置校验（preconditions）→ 规则校验（appliedRules，§3.6）→ 状态变更（postconditions）→ syncTriggers 联动；
- 每个 QUERY 行为 = 一个读方法（或走 M7）。

### 步骤 6：M5 → 系统管理配置

在 `seed.py` 的 `_seed_roles/_seed_permissions/_seed_resources/_seed_role_permissions` 中追加（保持幂等）：

1. 角色 `sys_role`（`code=roleId`，`parent_id` 表达继承）；
2. 权限 `sys_permission`（`code=permissionId`，`target_type/target_ref/data_scope`）；
3. 角色-权限 `sys_role_permission`；
4. 菜单资源见步骤 8。

> 注意：种子只在空库时全量写入，增量开发时若库已存在，需删 `backend/data/` 重建，或在 `ensure_seed` 中增加幂等的"按 code 存在即跳过"逻辑。

## 5. 系统管理与流程引擎的模型驱动配置

### 5.1 M5 主体模型 → 系统管理

目标：把 M5 的 actor/role/permission 落地为 `sys_*` 表，并让登录、鉴权、菜单自动生效。

**示例（新增"财务经理"角色及其审批权限）：**

M5 YAML：

```yaml
roles:
  - roleId: ROLE-FINANCE-MANAGER
    name: 财务经理
    inheritsFrom: [ROLE-FINANCE]
    permissions:
      - PERM-CONTRACT-APPROVE-FINANCE
permissions:
  - permissionId: PERM-CONTRACT-APPROVE-FINANCE
    targetType: BEHAVIOR
    targetRef: Contract_ApproveFinance
    dataScope: ALL
```

落地：

1. `sys_role`：`(name='财务经理', code='ROLE-FINANCE-MANAGER', parent_id=<ROLE-FINANCE 的 id>)`；
2. `sys_permission`：`(code='PERM-CONTRACT-APPROVE-FINANCE', target_type='BEHAVIOR', target_ref='Contract_ApproveFinance', data_scope='ALL')`；
3. `sys_role_permission`：关联该角色与该权限；
4. `sys_user_role`：把某个用户（如 `fm_user`）绑定到该角色。

效果：

- 登录后 `auth_service.get_permission_codes` 会递归父角色，汇总出该用户的权限码集合；
- `@require_permission('PERM-CONTRACT-APPROVE-FINANCE')`（或你的业务权限码）即可保护审批接口；
- 菜单可见性由 `get_menus` 按 `resource.permission_code` 过滤。

> 角色继承（`inheritsFrom`）落地为 `sys_role.parent_id`；`auth_service.get_user_roles` 已实现向上递归，无需改代码。

### 5.2 M6 流程模型 → 流程引擎

目标：把 M6 的 flow 落地为 `flow_definition`，让提交后能自动启动实例、逐节点审批。

M6 → node_graph 的转换规则（已在 §2.5 给出对照）：

- 每个 `activity` → 一个 node（`id=activityId`, `type` 映射见下）；
- 每个 `nextActivities` → 一条 edge（`source=当前`, `target=后继`）；
- 审批节点的不同结果，通过**边上的 `approval_outcome`** 区分（APPROVE/REJECT/RETURN）；
- `END` 节点用 `result` 标注 `APPROVED` / `REJECTED`，引擎据此把实例置为"通过/驳回"。

activityType → node.type 映射：

| M6 activityType | node.type |
|---|---|
| START | `start` |
| END | `end` |
| USER_TASK | `user_task` |
| APPROVAL_TASK | `approval_task` |
| SYSTEM_TASK | `system_task` |
| BEHAVIOR_CALL | `behavior_call` |
| SUB_FLOW_CALL | `sub_flow_call` |
| GATEWAY | `gateway` |

## 6. 工作流审批功能的完整实现（端到端）

以一个带审批的新业务功能为例，说明与流程引擎的配合方式。

### 6.1 审批对象与状态机

在 M1 中定义对象生命周期状态（如 `lifecycle: [草稿, 待财务经理审批, 待总经理审批, 已通过, 已驳回]`），并在业务表建 `status` 字段。

### 6.2 定义 M6 审批流（见 §5.2）

`flowType=APPROVAL`，`trigger.triggerType=BEHAVIOR`、`trigger.behaviorRef=Contract_Submit`（提交行为即流程入口）。

### 6.3 提交行为启动流程

`Contract_Submit` 行为（service）在事务内：

1. 校验规则（appliedRules）；
2. `status → 待财务经理审批`；
3. 调 `FlowEngine.start(definition_id, business_key, business_object_refs, variables, creator_id)`；
4. 把返回的 `instance_id` 回写到业务记录（`instance_id` 字段），并与当前活动联动。

> 引擎启动后，会按 start 节点的后继创建首个 `approval_task`，并通过 `role_ref` 解析出办理人（`_resolve_assignee`：查 `sys_user_role` 关联 `sys_role.code=role_ref` 的第一个启用用户）。**因此角色必须在步骤 6 已配置好、且有用户绑定，否则任务无办理人。**

### 6.4 工作台审批处理

审批人在"审批中心 → 我的待办"处理，调用 `/api/workbench/todo/{id}/approve|reject|return`，后端 `workbench_service` 在**同一事务**内：

1. 校验任务归属与状态；
2. `engine.approve/reject/return_to(...)`；
3. `sync_status_from_instance(...)` 把流程状态映射回业务对象状态：
   - 实例 `APPROVED` → 业务 `已通过`；
   - 实例 `REJECTED` → 业务 `已驳回`；
   - 实例 `RUNNING` → 按当前 TODO 任务的 `role_ref` 映射为"待 XX 审批"。

### 6.5 与流程引擎的配合点清单

| 配合点 | 做法 |
|---|---|
| 流程定义来源 | M6 → `flow_definition.node_graph`（§5.2） |
| 审批人解析 | `role_ref` → `sys_role.code` → `sys_user_role` → 首个启用用户（可扩展为多人会签/按数据范围分配） |
| 状态回写 | 引擎更新 `flow_instance.status` + `flow_task`，业务侧经 `sync_status_from_instance` 同步 `status` |
| 职责分离（禁止自批） | 在审批行为（M2 的 `Contract_ApproveXxx`）中校验 `审批人 != 提交人`（引用 M3 `RULE-APPROVAL-SOD`） |
| 通过后的联动 | 通过后若需改变业务状态/触发下游，用 M2 `syncTriggers` 或审批流末尾的 `behavior_call`/`system_task` 节点 |
| 撤回 | 首个审批人处理前，提交人可撤回（终止实例、业务回草稿），参考 `customer_service.withdraw` |

### 6.6 退回 / 撤回 / 驳回

- **驳回（REJECT）**：实例进入 `REJECTED`，业务回"已驳回"，可修改后重新提交（创建新实例）；
- **退回（RETURN）**：`engine.return_to(task_id, target_activity_id, ...)` 取消当前任务、在目标活动重新生成 TODO 任务；
- **撤回（WITHDRAW）**：首活动未处理时终止实例、业务回草稿。

>
> 复制后按本章 §7.2～§7.8 的协议要求改造（替换业务域提示词与工具清单），底座 `techbase/` 不含上述任何文件，必须补齐。

### 7.1 架构定位

AI 编排层位于"后端服务层"之上，**复用同一套后端能力**：

```
前端 AI 对话组件 (SSE 流式渲染)
  └─ POST /api/ai/chat  (SSE)
        └─ AI 编排层 (ai/ + sse/)
              ├─ DeepSeek 客户端
              ├─ 系统提示词构建（读 Ontology Registry）
              ├─ 工具注册（导航/查询/行为/只读 SQL）
              └─ 只读 SQL 白名单控制器 (sql_readonly/)
```

### 7.2 配置 DeepSeek

`backend/config.yaml` 的 `ai` 段（及独立 `deepseek.config.yaml`，参考架构文档 §15.2）：

```yaml
ai:
  enabled: true
  provider: deepseek
  api_key: "sk-xxxx"            # 或从 .env 读取，禁止硬编码
  base_url: "https://api.deepseek.com"
  model: "deepseek-chat"
```

### 7.3 系统提示词构建（基于本体注册表）

每次对话注入动态 system prompt，至少包含：

1. 系统角色与能力说明；
2. 可用功能/行为/查询清单（来自 `registry["behaviors"]`、`registry["query_reports"]`）；
3. 可用工具清单及调用说明（导航/查询/行为/SQL 只读）；
4. 只读安全边界（不得写数据）；
5. 渲染协议约定（何时返回 text/table/chart/action）。

### 7.4 工具注册（Function Calling）

由注册表自动生成工具 schema，分类如下（架构文档 §9.6）：

| 工具 | 来源 | 说明 |
|---|---|---|
| 页面导航 | `registry["menus"]`/`screens` | 打开某录入/查询页 |
| 查询工具 | M2 QUERY / M7 | 执行某列表查询、取详情 |
| 行为工具 | M2 COMMAND | 执行某录入/提交/审批（受权限边界约束） |
| 图表工具 | 查询结果 | 转柱状/折线/饼图（ECharts） |
| SQL 只读工具 | `registry["db_whitelist"]` | 无现成 API 时的只读查询兜底 |

### 7.5 SSE 流式输出协议

后端 `sse/` 按以下分片推送（架构文档 §14.2）：

```
message_start → delta* → (tool_call | tool_result)* → render_payload → message_end
```

前端 `ReadableStream` 逐片读取，增量拼接文本、展示"正在查询…"状态、最终切换为结构化渲染。

### 7.6 结果渲染协议

| 渲染类型 | 触发场景 |
|---|---|
| `text` | 状态反馈、业务说明、执行结果 |
| `table` | 列表、统计、结构化查询结果（复用与固定页面同一套表格 CSS） |
| `chart` | 趋势、分布、统计图（ECharts） |
| `action` | 引导打开页面、查看详情、执行行为 |

### 7.7 安全边界（强制）

1. AI 对话默认**只读**，禁止写数据；
2. 写操作必须走固定页面的行为工具，且受权限边界约束；
3. 动态 SQL 严格只读：仅 `SELECT`、仅白名单表/字段、强制 `LIMIT`、禁多语句、执行超时、记录审计（架构文档 §10）；
4. 所有工具调用记录审计日志（`audit_logs`）。

### 7.8 前端 AI 对话组件

将 `AdminLayout.tsx` 中右侧占位替换为真实对话组件：

- 消息区：用户右对齐品牌蓝底白字、AI 左对齐白底（UI-UE §3.4）；
- 输入区：圆角 textarea + 品牌蓝发送按钮；
- 支持 `text/table/chart/action` 四类渲染，表格/状态标签复用全局 CSS 类。

## 8. 其它补充约定

1. **可追溯门禁**：M2 中 `triggerType=USER_ACTION` 的行为必须被至少一个 MU 操作功能点引用；MU 引用的行为必须存在（框架 §1.3.7）。
2. **一致性约束**：M2 `queryReportRef` ↔ M7 `behaviorRef` 严格一对一；M6 的 `roleRef`/`behaviorRef`/`subFlowRef` 必须引用存在的模型元素。
3. **事务边界**：一个行为只改一个聚合（聚合内主从同事务）；跨聚合靠 syncTriggers 或流程编排。
4. **逻辑删除**：所有业务数据删除用 `flag=0`，历史保留；被引用的主数据不可删只能停用。
5. **状态机**：对象状态迁移严格按 M1 `lifecycle` + M2 postconditions + M6 结果，不出现模型外状态。
6. **版本管理**：模型文件内维护 `version`，破坏性变更记录 `CHANGELOG.md`。
7. **审计**：关键写操作与 AI 工具调用写入 `audit_logs`。

## 附录 C：术语对照

| 术语 | 说明 |
|---|---|
| 本体模型 | 业务语义的唯一来源；七模型（M1/M2/M3/M5/M6/M7/MU）或十一模型（+M4/ME/MI/MM），见 §0.6 |
| 技术底座 | 只读技术基线：`techbase/`（Python·七模型）或 `jjy-ontology-base/`（Java·十一模型） |
| 唯一语义源 | 同一事实只在一个地方定义；跨处引用而非复制 |
| 编译期投影 | 构建期由 M1+MM 生成 PO 与 DDL（Java 栈） |
| 运行期投影 | 启动期加载 YAML 进 `ModelRegistry` / `registry`，驱动运行时行为 |
| 达成判据 L1–L4 | 已声明 / 已实现 / 已接通 / 可验收，见 §0.7 |
| 漂移守门员 | commit/push 时比对模型与代码，有漂移即拒绝提交，见 §0.8 |
| 对账 | 机械比对模型声明与代码/数据库实体，输出覆盖率 |
| 跳选框（POPUP_SELECT） | 对象引用字段的界面控件：文本框 + 弹窗选择 |
| node_graph | 流程引擎使用的 JSON 流程定义（nodes + edges） |
| syncTriggers | M2 行为成功后同步调用下游行为的跨对象联动（七模型路线） |
| producedEvents / subscribedEvents | M2 行为产出 / 订阅的事件（十一模型路线，跨聚合联动唯一通道） |
| outbox | 与业务写同事务的事件箱，保证事件不丢 |
| 逻辑删除 | `flag=0` 标记删除，保留历史 |
| AI 编排层 | 意图识别 / 能力路由 / 工具调用 / 渲染 |
| manifest.json | 模型登记表：新契约含 sha256，启动期校验 |
